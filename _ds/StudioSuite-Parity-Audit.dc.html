1 · What was compared, and how

Each web module was read at source and walked control by control, then matched against the mobile build (StudioSuite-Mobile.dc.html) and the Expo screen map. A control counts as present only when the mobile side has a bound handler that produces the same result — not merely a lookalike element.

  • Finance — finance.jsx · finance-core.jsx · finance-tabs.jsx · finance-audit.jsx, read in full against the mobile finance engine and its six tabs.
  • Studio admin and client portal — admin.jsx · client.jsx · documents.jsx · pricing.jsx, control inventory compared against the mobile equivalents.
  • Public site — landing.jsx, compared against the mobile marketing surface.
  • The standing interaction gate (StudioSuite-E2E.dc.html) remains the check for dead controls, unbound inputs and tap-target floors; it walks each surface at handset and desktop width.

4 · Open items — your call

A · Public “Reserve a Date” flow

The web landing page carries a three-step booking modal — month calendar, contact details, confirmation — reachable from the header, the hero and each package card. The mobile marketing page shows the packages but routes every intent to sign-in or Luma, so a prospective client cannot hold a date from their phone. This is the largest remaining functional difference. Recommended: a bottom-sheet version of the same three steps, with a month grid sized to 44pt targets.

B · Persistence of finance edits closed

Closed. The prototype now stores bookkeeping settings, the expense register, manually raised invoices, payment overrides, the hash-chained audit log, the selected period and the studio registers (staff, roster, suppliers, contacts) in local storage under studiosuite.v1, matching desktop; transient UI — open sheets, form drafts, searches, password gates — is deliberately not kept. The acceptance crawler loads every surface with &nopersist=1 so its synthetic clicks never enter the studio's books. The native app would use device storage on the same key set.

C · Two decorative desktop buttons

“New Booking” on Bookings and “Add Contact” on Contacts exist on the web but have no handler there either — they are placeholders, and mobile omits them rather than copying dead controls. If they should become real, they need designing once and building on both.

5 · Re-verification

The surfaces added since the last full pass — Studio Staff (roster and contracts) and Finance → Suppliers — were crawled at 390px and 1280px through the interaction gate, which now deep-links every finance tab and staff segment directly. One real defect was found and fixed: the engagement-type, pay-basis, agreement-type and contract-status chips were 42px tall and are now 44px. Handler wiring, controlled inputs and thrown errors came back clean across all six runs.

Two caveats on the method. The inert-click test compares markup length, so a chip that swaps one style string for another of equal length reads as inert; those lines are informational, not failures. And the 12-width layout matrix depends on the app's ResizeObserver, which only fires when the browser grants a rendering opportunity — in a background preview that is roughly once every ten seconds — so the matrix is skipped in the quick crawl and belongs to StudioSuite-Matrix-Probe.dc.html, run with the tab in front. One open observation from the desktop runs: a 60×17 nav target is measured mid-crawl at 1280px, which looks like phone chrome being measured before the app has re-laid out for the wider frame rather than a defect in the design — worth confirming on a focused run.
